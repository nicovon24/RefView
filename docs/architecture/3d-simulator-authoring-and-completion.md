# 3D simulator: architecture, authoring and completion plan

This document records the current browser-based 3D approach and an incremental path to a reviewed, playable incident. It is an architecture note, not a second task board. The authoritative status of every ticket is in [`docs/specs/tasks.md`](../specs/tasks.md). The seven [system-design SVGs](../system-design/README.md) are visual companions.

## Current system and ownership

RefView is a Next.js App Router product with strict TypeScript. Its simulator is a purpose-built browser runtime on Three.js and React Three Fiber (R3F), not a general game engine. R3F mounts the canvas and manages the React lifecycle. Imperative Three scene objects are created and updated inside that canvas. The scene groups the field, markings, goals, stadium, light, seven skinned footballers, a separate referee, the ball and camera. The authored incident preview and local playtest use the selected Quaternius player resources and shared pose/scene adapters. The referee uses the same resource family with a black kit and distance-driven Idle/Walk/Jog presentation. The current local routes are explicitly unsaved and unscored.

One canonical 60 Hz tick is the timing key. Authored tracks supply player and ball roots and public event timing. The exact-scene adapter applies frame roots, clip phases and absolute skeletal poses, then renders the camera view. Seeking or replaying a tick must reconstruct the same pose. Referee input controls observation position and view; it does not rewrite the incident. The player/ball contact event at tick 366, the football facts and the answer key belong to the authored source. Physics can later support local movement and collision, but cannot decide the reviewed foul. Rapier is a selected technical direction in [`technology-stack.md`](technology-stack.md), not an active dependency of the current incident scene.

The domain, simulation and content packages define validation, timeline, observation and deterministic evaluation. A full v2 authored scenario includes competition profile, tracks, assets, geometry bindings, official sources, private evidence, rubric and prepared bilingual debrief. Its compiler validates and derives versioned public/private projections and hashes. PostgreSQL/Prisma attempt and publication foundations exist and have isolated tests, but the local WebGL route is not yet wired into an approved browser-to-PostgreSQL scored journey. XState-based local workflow work likewise does not turn the preview into a published training incident. The optional AI Coach may explain an already evaluated attempt; it never creates facts, sets the answer or changes a score.

## Why keep the browser runtime

The present product needs one authored incident with deterministic camera-dependent observation, replay and scoring inside a bilingual web application. Three/R3F already serves the incident, integrates with Next.js, and keeps the canonical TypeScript contracts close to the presentation. Moving to Unity now would require rebuilding the scene, web integration and evidence-capture path before it improves the visible contact problem. The leverage is in better rigged clips, asset validation and authoring tools. Reconsider a full engine only if the product commits to continuous autonomous matches, complex agent behavior, broad live physics, or desktop/console distribution. That would be a new architecture decision with measured requirements, not a prerequisite for this incident.

## Hybrid asset and authoring workflow

1. **Football brief and evidence design.** Freeze the reviewed action, official-law edition, actor roles, observable contact feature, A/B camera positions and required evidence before editing pixels. The current onside buildup, careless trip and penalty/no-card target are authored facts, while rendered observation approval remains open.
2. **Blender source work (proposed).** Retain editable source files for football-specific footwork, challenge, balance recovery and the forward fall. Use a shared skeleton, measured scale and stable bone/attachment names. Blender is an authoring tool; it does not own the final incident clock or facts.
3. **glTF/GLB export.** Export rigged geometry and compatible named clips. Record the exporter and source revision. The present selected resource set includes glTF resources, binaries, textures and animation GLB files; other current incident resources are procedural modules. The diagram is a target workflow, not a claim that every asset is already a single GLB.
4. **Asset gate.** Verify exact bytes, license text, origin/creator, download date, hashes, texture/material closure, units, skeleton hierarchy, clip ranges, root motion, bounding geometry, attachments and browser load cost. Reject undeclared remote dependencies. Preserve a versioned manifest and serve exact verified public bytes.
5. **RefView scenario authoring.** Today the incident is assembled in code and contracts. A future visual editor should set actor and ball keyframes, camera witnesses, clip placement/transitions, safe cues, evidence anchors, occluders and the decision window. It should export validated canonical source, rather than store a separate truth. Editing football facts, rulings and rubric requires explicit reviewed fields and a new source version.
6. **Compile and inspect.** Compile public/private projections and exact resource identity. Use fixed ticks and normal-speed A/B playback to inspect foot planting, contact, screening, ball visibility, referee movement and the final fall pose. Replay, seek, pause and restart must preserve exact outcomes.
7. **Review and publish.** A human reviews the actual rendered evidence and legal meaning. Bind captures to exact source bytes, assets, renderer and immutable running build before a scenario enters a reviewed catalog. That binding and the selected rig's observation calibration are still open.

Clip names should express a stable action and version, for example `run_forward_v1`, `challenge_step_v1` and `fall_forward_brace_v1`. Store trim ranges, intended speed range, loop/one-shot behavior, root-motion policy, entry/exit pose, contact anchors and floor clearance beside the exported bytes. The canonical timeline selects clip phase; an independent animation mixer clock must never become a second source of time. For the current candidate, preserve player/ball roots and the exact tick 330–480 suffix unless a reviewed source version deliberately changes them.

## Work needed to finish the first simulation

The order below follows dependencies in the [canonical tracker](../specs/tasks.md); it does not assign new statuses.

1. **Finish the selected rig and visible incident (RV-019E, RV-005, RV-008).** Audit the full motion sequence at normal speed and fixed ticks, including steady opening runs, the challenge, fall rest and referee travel. The recent local changes improved those motions. The unresolved acceptance issue is selecting an actual visible exterior contact feature and recalibrating observation against the posed selected meshes. Recheck A/B readability and nuisance occlusion with fresh captures after any relevant render change. Keep the football facts, pass/contact timing and rubric under source authority.
2. **Complete trusted review and admission (RV-006, RV-008).** Bind reviewed visual evidence to exact source/asset bytes and a verified immutable running build. The pinned restore contract already has isolated PostgreSQL evidence; connect that proven behavior to the real incident's browser flow, then finish import/publication and admission. Synthetic isolated review records used in persistence tests do not publish this incident.
3. **Connect the complete simulator journey (RV-007, RV-009).** Wire live controls and C2 observation capture into the authored scene, then briefing, play, decision gate, deterministic evaluation, prepared debrief, canonical replay, retry and recovery. The current unsaved local preview is the presentation proving ground for this integration.
4. **Complete product interface and MVP acceptance (RV-010, RV-011).** Verify Spanish-first and English flows, camera/input preferences, accessible controls, loading and failure states, desktop/mobile behavior, visual WebGL acceptance, named device/browser performance and the real browser-to-PostgreSQL attempt. Obtain independent review after final relevant edits.
5. **Develop the reusable authoring pipeline.** Introduce Blender source and football clip checks only where they close measured motion or contact gaps. Build the visual editor in slices after the first incident's source contract and publication workflow are stable: placement/timeline first, then camera/evidence preview, then validation/export. The editor must produce the same versioned source accepted by the compiler. This is a proposed follow-on capability; the tracker should receive bounded tasks before implementation begins.

Expanded sessions, assistant/VAR perspectives, Academy, Community, Assessment and optional hosted Coach work have their own later contracts and dependencies in the tracker. They are not prerequisites for calling the *first incident* complete.

## Definition of done for the first incident

A reviewer can open a published, versioned incident; see the approved facts from meaningful A/B positions; move the referee; make one guarded decision; receive deterministic penalty/no-card evaluation and a sourced Spanish/English debrief; replay the same canonical timeline; and recover an owner-bound attempt from PostgreSQL. Fixed-tick and normal-speed WebGL evidence must match the reviewed source, asset and running-build identity. Tests must cover timeline/observation/evaluation/authority, with real PostgreSQL for persistence, Playwright CLI for browser flows, visual inspection for contact readability, and an independent final review. The experience must work with no AI provider.

The largest current blockers are visual contact calibration for the selected rig, trusted evidence/build binding for publication, and wiring the local scene to the scored attempt flow. Scene polish alone cannot close those gates. Asset origin and exact license evidence must remain attached to each imported byte; selected Quaternius resources have their existing recorded CC0 evidence, while any newly sourced clip needs its own check.
