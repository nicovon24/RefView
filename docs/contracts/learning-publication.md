## Academy content and publication contract v1

### Authority and identity

- A lesson is addressed by stable `lessonId` and positive integer `version`; its immutable source has a server-derived canonical content hash. A changed translation, explanation, reference, example, answer, or practice mapping creates a new version.
- The v1 hash input is the normalized exact record `{ schemaVersion: 1, lessonId, version, lawsEdition, topicId, level, localized: { es, en }, example, officialSources, preparedFollowUps, practiceRefs }`. `localized` contains the full visible explanation/technical text; `example` contains separately labelled facts, observable evidence, interpretation, and rule application in both languages. Source and follow-up arrays are sorted by stable IDs before hashing. Unknown fields, duplicate IDs, nonfinite values, and missing locale fields are rejected. Publication state, reviewer metadata, and timestamps are excluded from the immutable source.
- The server computes `sha256:` plus lowercase SHA-256 of UTF-8 `canonicalJsonV2(["refview-academy-lesson-v1", normalizedSource])`, using the existing canonical JSON semantics in `packages/content/src/source-core-v2.ts`. It recomputes and compares that value on stored reads; caller-supplied hashes are never authority. The implementation must prove canonicalization and payload coverage with tests before publication.
- Every lesson declares one exact Laws edition, topic and difficulty. Official references include the publisher, edition, language, direct edition-pinned document URL, law/section and printed page, inspection date, and inspected artifact digest. Mutable `latest` URLs may be convenience links but do not establish version identity.
- Spanish and English share the same reviewed facts, interpretation boundaries, rule application, and references. Copy differences are editorial, never separate answer keys.
- The lesson source separates scenario/example facts, evidence available to the learner, referee interpretation, and rule application. A rule citation never asserts that an illustrated animation establishes an incident fact.

#### Executable v1 source shape

The normalized exact record uses these nested shapes; all text is nonempty, trimmed, bounded to an implementation-declared length, and stored as authored UTF-8 without HTML. Arrays reject duplicate IDs and are sorted before hashing. A schema change requires a new `schemaVersion` and hash domain tag.

| Field | Exact v1 shape and validation |
| --- | --- |
| `lessonId` | lowercase ASCII slug `[a-z0-9]+(?:-[a-z0-9]+)*` |
| `version` | positive safe integer |
| `lawsEdition` | literal `IFAB-2026-27`; a later edition needs an explicit schema/edition update |
| `topicId` | v1 literal `challenge`; a later taxonomy expansion is versioned |
| `level` | `beginner`, `intermediate`, or `advanced` |
| `localized` | exact `{ es: { title, lead, plainExplanation, technicalExplanation }, en: { title, lead, plainExplanation, technicalExplanation } }` with string fields |
| `example` | exact `{ facts, evidence, interpretation, ruleApplication }`, each a `{ es: string, en: string }` pair; facts are explicitly labelled as authored in the UI |
| `officialSources` | nonempty array of exact `{ sourceId, publisher: "IFAB", edition: "IFAB-2026-27", language: "es" \| "en", documentUrl, lawNumber, sectionCode, displayLabel, printedPage, inspectedAt, inspectedArtifactSha256 }`; `lawNumber` is an integer 1–17 and `sectionCode` is a language-neutral ASCII locator such as `12.1`, `1.6`, or `14.intro`. `displayLabel` is localized text only; coverage compares `(lawNumber,sectionCode)` pairs, requiring the same set in both languages. `sourceId` is a stable slug unique within the lesson, `printedPage` is a positive integer, digest is `sha256:` plus 64 lowercase hex digits, and URL must be an edition-pinned HTTPS IFAB document. Require at least one source per locale; sort by `sourceId` |
| `preparedFollowUps` | array of exact `{ followUpId, question: { es, en }, answer: { es, en }, sourceIds: { es: string[], en: string[] } }`; each locale's nonempty source IDs resolve only to same-language `officialSources`, sorted uniquely; sort entries by `followUpId` |
| `practiceRefs` | array of exact `{ kind: "assessment" \| "scenario", targetId, targetVersion, topicId, lawsEdition }`; stable target slug/positive version, `topicId` and `lawsEdition` equal the lesson's values, sort by `(kind,targetId,targetVersion)` and reject duplicates |

The document URLs for the initial lesson are exact allowlisted edition-pinned IFAB URLs recorded below. A future source URL requires review and schema validation before publication. Normalization does not silently drop unknown keys or invent missing translation fields. Cross-locale semantic equivalence is a human review assertion bound to the hash, not something a string validator can prove.

### Publication

- Draft content is available only in an explicitly labelled editorial preview and is excluded from public Academy discovery, recommendations, and scoring.
- Publication requires a persisted review record bound to `lessonId`, `version`, and the server-derived content hash, with Nicolas's trusted reviewer principal, review time, source/provenance evidence, translation-equivalence decision, and football-content decision. Importing that record requires a separately reviewed administrator attribution path; a client assertion or approval boolean is insufficient. No automatic promotion from draft is allowed.
- Publication and retirement are authenticated administrator transitions that reference an existing valid bound review record, use monotonically increasing revisions, and append events recording actor, time, reason, prior/next state, version, and content hash. The mutation revalidates the stored source and review binding in one transaction. A retired lesson leaves historical references resolvable but is not newly discoverable or recommendable.
- The persistence plan uses PostgreSQL `LessonVersion` keyed by `(lessonId, version)` and additionally unique on `(lessonId, version, contentHash)`, with normalized source JSON and creation time; `LessonReviewRecord` keyed by review ID and foreign-keyed to that unique triple with trusted reviewer principal and review evidence; `LessonPublication` keyed by `(lessonId, version)` with state/revision and optional bound review ID; and append-only `LessonPublicationEvent` unique on `(lessonId, version, nextRevision)`. The publish/retire transaction locks publication state, recompiles the stored source, verifies its hash and bound review, enforces expected revision and allowed transition, then updates state and appends one event. Published source rows are never updated in place. Exact Prisma migration and administrator admission still require independent persistence/authority review before implementation.

### Prepared follow-ups and practice

- Prepared follow-up questions and answers are versioned lesson content. They cite the lesson's source IDs and are visibly labelled as prepared responses; they need no AI provider and cannot modify any attempt or score.
- A related-practice reference stores only target kind, stable ID/version, topic, and Laws edition. Current eligibility is derived at read time from the target's reviewed publication/retirement state and topic/edition compatibility; no stored eligibility flag is trusted. Only a currently eligible target appears as a working link. The local unsaved simulator playtest is ineligible.
- When no compatible target exists, the UI states that practice is not available yet. It never routes to an unrelated or unpublished exercise.

### Required negative cases

- Reject duplicate lesson ID/version or a changed payload under an existing hash.
- Reject missing source edition, section, page, attribution, inspection digest, or divergent locale meaning.
- Reject mixed-edition references and practice targets, unpublished/retired target links, and draft lesson discovery.
- Reject publication without bound content and review records; reject a stale revision or attempted mutation of published bytes.

## Assessment authority and attempt contract v1

### Scope and content identity

- V1 has three authored types: `ruleQuestion` (one opaque option), `restartDiscipline` (a structured stop/restart/card choice), and `authoredIncidentAnalysis` (written facts and learner-visible evidence, structured decision, and required short reasoning). A text item never claims to assess simulator positioning or perception.
- Every item pins stable `itemId`, positive `version`, `IFAB-2026-27` edition, topic, level, type, exact bilingual prompt and options, reviewed source locators, private accepted alternatives, rubric, correction, and compatible recommendations. The server computes an immutable canonical source hash over all public and private authored content. Changing a translation, answer, rubric, alternative, correction, or recommendation creates a new version. Source parsing rejects missing translations, duplicate IDs, unknown fields, nonfinite numbers, and mixed editions.
- A trusted Nicolas review record binds the exact item ID/version/hash, football interpretation, accepted alternatives, source evidence, and Spanish/English equivalence. A separately reviewed administrator path admits the record and publishes or retires a version transactionally with actor/reason/revision events. An unpublished item cannot enter catalog or new attempts; retirement blocks new attempts but preserves owner-bound historical results and pinned active attempts.
- V1 can use authored textual incident facts independently of the rendered simulator only when the text is separately reviewed. It must not borrow an uncalibrated animation as evidence. Simulator-derived observation questions wait for RV-011.

#### Executable v1 domains and source

The v1 catalog domain is exactly `lawsEdition="IFAB-2026-27"`, `topicId="challenge"`, and `level="beginner" | "intermediate" | "advanced"`. The catalog query accepts optional exact filters from those enums. It returns available counts for each level and explicit zero/unavailable states for valid combinations with no published item; unknown filters are rejected. Adding an edition/topic needs a reviewed domain version. The first starter set may contain only the levels actually reviewed; the UI must not imply all three exist.

The normalized item source is an exact object `{ schemaVersion: 1, itemId, version, lawsEdition, topicId, level, type, localized, publicEvidence, inputSpec, privateRubric, correction, officialSources, recommendationRefs }`. IDs are lowercase ASCII slugs; versions are positive safe integers. `localized` is exactly `{ es: { title, prompt }, en: { title, prompt } }`; all text is plain, nonempty, trimmed UTF-8. `publicEvidence` is a sorted array of `{ evidenceId, text: { es, en } }` with unique IDs. `officialSources` has the same exact source shape, edition-pinned IFAB URL allowlist, bilingual `(lawNumber,sectionCode)` coverage rule, and digest validation as Academy v1; source IDs are unique. The source has no functions, HTML, unknown fields, or mutable publication metadata.

`inputSpec` is a discriminated exact shape:

| `type` | Exact public input spec |
| --- | --- |
| `ruleQuestion` | `{ kind: "ruleQuestion", options: [{ optionId, label: { es, en } }] }`, 2–5 unique opaque option IDs sorted by ID |
| `restartDiscipline` | `{ kind: "restartDiscipline", offenderHandles: string[] }`, unique public handles from the authored textual roster; may be empty when offender selection is not asked |
| `authoredIncidentAnalysis` | `{ kind: "authoredIncidentAnalysis", offenderHandles: string[], reasoningRequired: true, reasoningMaxCodePoints: 600 }`; authored facts are in `publicEvidence` and the prompt, not a simulator trace |

The canonical public answer for `ruleQuestion` is exactly `{ kind: "ruleQuestion", optionId }`. For the other two types it is exactly `{ kind, stopPlay, restart, discipline, offenderHandle }`, plus `reasoning` for `authoredIncidentAnalysis`. `restart` is `playOn | penaltyKick | directFreeKick | indirectFreeKick | droppedBall`; `discipline` is `none | yellow | red`; `offenderHandle` is null or a handle from the public spec. `stopPlay` equals `restart !== "playOn"`; a card requires a non-null offender, and a non-null offender is rejected when the roster is empty. All enum values are structurally valid, including wrong answers. A browser submission never includes item source, rubric, result, or owner ID.

`privateRubric` is exactly `{ rubricVersion: 1, acceptedAnswers, reasoningDimensions }`. `acceptedAnswers` is a nonempty unique array of normalized canonical answer shapes **without reasoning**, sorted by canonical JSON; every option/handle resolves in `inputSpec`, and structurally impossible choices fail source validation. A `ruleQuestion` rubric accepts option IDs; structured rubrics accept exact semantic tuples. `reasoningDimensions` is `[]` for types without reasoning and exactly three `{ dimensionId, prompt: { es, en }, status: "unscored" }` entries for `authoredIncidentAnalysis`, with IDs `relevantFact`, `ruleConnection`, and `decisionJustification`. Their displayed results always have `score: null`; an algorithm cannot infer a prose grade. An inconclusive or interpretative item must have explicitly reviewed accepted alternatives and correction language explaining the uncertainty.

`correction` is exactly `{ correctionVersion: 1, summary: { es, en }, explanation: { es, en }, evidenceIds: string[], sourceIds: { es: string[], en: string[] } }`. `evidenceIds` is nonempty, so `publicEvidence` must contain a matching learner-visible item; every ID resolves to it. Each locale's nonempty source IDs resolve only to that locale's official sources. `recommendationRefs` is a sorted unique array of `{ targetItemId, targetVersion, topicId, lawsEdition }` matching the current item topic/edition; it contains no URL or cached availability. Empty is allowed until a compatible reviewed target exists. All arrays reject duplicates and have explicit implementation caps before storage.

The server hashes `sha256:` plus lowercase SHA-256 of UTF-8 `canonicalJsonV2(["refview-assessment-item-v1", normalizedSource])`, using the existing `packages/content/src/source-core-v2.ts` semantics. It recomputes this on stored reads; caller hashes are not trusted. `privateRubric` is included in the source hash; the result separately pins `rubricVersion=1` and the hash of `canonicalJsonV2(["refview-assessment-rubric-v1", normalizedSource.privateRubric])`. A source revision changes the item version, never bytes under a prior `(itemId,version)`.

### Public and private projections

- Catalog reads expose only currently published item metadata: ID/version, edition, topic, level, type, brief title, and availability. A started attempt exposes only the pinned public prompt/options, allowed input schema, learner-visible evidence, and the current owner's opaque attempt ID.
- Accepted answers, scoring mappings, private rubric, prepared correction, reveal reasons, and recommendation reasons remain server-only during an active attempt. Explicit DTO allowlists apply to Server Component props, Server Action responses, metadata, prefetched routes, logs, and client bundles. CSS-hidden answers are not protected.
- An owner-bound finalized result may reveal only a reviewed correction projection: the submitted initial answer and reasoning, accepted outcome/alternatives where applicable, explanatory evidence and rule references, separate dimension results, and currently eligible next practice. The private rubric itself is never serialized.
- Prepared explanation or an AI Coach cannot change the immutable submission or score.

### Input and evaluation

- The server accepts structurally valid wrong answers. It rejects impossible stop/restart combinations, unknown option IDs, unsupported actor handles, undeclared fields, client-supplied scores, and oversized reasoning. All submitted text is plain UTF-8, bounded, and preserved under one declared normalization. A confirmed answer and reasoning are immutable; another try is a new attempt.
- Only reviewed exact semantic alternatives score the structured answer: `100` when accepted, `0` when a valid answer is not accepted. Partial credit needs a new reviewed rubric version. Interpretative or inconclusive items need explicit accepted alternatives and language that does not imply unsupported certainty. There is no overall grade.
- Written reasoning is required for `authoredIncidentAnalysis` and saved with the initial answer, but v1 labels each of the three declared rubric dimensions `unscored` with `score: null`. Their prepared prompts guide self-review; they are not automatic grading. A structured evidence/rule selection, if introduced later, is a separate dimension. Positioning, communication, and VAR protocol are `notApplicable` unless an item actually collects reviewed inputs for those dimensions. Assessment-specific `unscored` must not be mapped to the simulator's `insufficientEvidence` status.
- The durable attempt/result pair pins item ID/version/source hash, rubric version/hash, evaluation algorithm version, correction version, source edition, and server `startedAt`/`finalizedAt` timestamps. The exact evaluation payload below contains the scoring fields; attempt/result metadata stores the edition and timestamps. The owner-bound result projection joins both without inventing an aggregate score.

Reasoning normalization is NFC, CRLF/CR to LF, and trim only at the start/end; the normalized value must be 1–600 Unicode code points with no NUL or disallowed controls. This exact normalized text is stored and shown back. The normalized canonical answer contains only declared keys and values; option/handle strings use the exact public IDs. The submission digest is `sha256:` plus lowercase SHA-256 of UTF-8 `canonicalJsonV2(["refview-assessment-submission-v1", itemId, version, contentHash, normalizedAnswer])`; it excludes the idempotency key and server timestamps. The result shape is exactly `{ itemId, version, contentHash, rubricVersion, rubricHash, algorithmVersion: 1, correctionVersion: 1, structuredDecision: { status: "scored", score: 0 | 100, reasonCodes: string[], evidenceIds: string[] }, reasoning: { status: "unscored", score: null, dimensions: [{ dimensionId, status: "unscored", score: null }] } | { status: "notApplicable", score: null, dimensions: [] }, positioning: { status: "notApplicable", score: null }, communication: { status: "notApplicable", score: null }, protocol: { status: "notApplicable", score: null } }`. `reasoning` is unscored only for the analysis type. Accepted answer means 100 with no mismatch code; a valid unaccepted answer means 0 with `answerMismatch`. `structuredDecision.evidenceIds` are the reviewed correction's authored rationale IDs, not proof of what a learner observed.

### Owner-bound PostgreSQL lifecycle

- Assessment versions, publication events, attempts, initial submissions, results, and idempotency claims have dedicated tables; simulator `Attempt`, `Decision`, and `Evaluation` are not reused. All owner-bound rows reference a valid anonymous session or future authenticated owner. The present cookie action only works against an isolated test database; production owner admission, expiry/purge, and final authority review are prerequisites to public mutations.
- The PostgreSQL plan has `AssessmentVersion` PK `(itemId,version)` and unique `(itemId,version,contentHash)` with immutable source JSON; `AssessmentReviewRecord` FK to that unique triple; `AssessmentPublication` PK `(itemId,version)`, checked `draft -> reviewed -> retired` state/revision and bound review ID; `AssessmentPublicationEvent` unique `(itemId,version,nextRevision)`; `AssessmentAttempt` PK `attemptId`, FK to immutable version triple and `AnonymousSession.id`, state `ready | finalized`; `AssessmentSubmission` unique `attemptId`; `AssessmentResult` unique `attemptId`; and `AssessmentFinalizationClaim` unique `(attemptId,idempotencyKey)`. Submission/result/claim rows FK to the attempt and never identify owner from a caller-supplied field. The transaction locks the attempt, verifies its session owner, and uses these unique constraints to enforce one initial submission/result. Review/admin transitions use a row lock, expected revision, trusted actor, and append-only event in the same transaction.
- On start, a same-origin Server Action resolves the valid cookie owner, locks the publication row, verifies current reviewed eligibility, and stores immutable item/rubric identity. The client cannot choose an owner or answer key.
- On confirm, a same-origin Server Action resolves the owner again, locks the attempt, validates and normalizes the exact bounded input, and derives the canonical payload digest server-side. It then checks scoped idempotency and an existing result **before** the active-state guard, comparing the newly derived digest. A new finalization atomically inserts one immutable initial submission, result, claim, and finalized state. A same-key/same-payload retry returns the prior owned result; a changed payload conflicts. A different key after finalization may alias the existing owned result only when its normalized digest matches; the transaction records the alias claim, returns the same result ID, and changes no submission/result bytes. A different digest conflicts. Concurrent differing keys create at most one result, enforced by PostgreSQL uniqueness. An uncertain client failure retains the exact choice and key until owner-bound restore resolves it.
- Result reads reauthorize the current owner every time, including after refresh. IDs and idempotency keys are never authorization. Owner-specific responses are private and uncached. An expired or missing owner gets no result.
- Current recommendation eligibility is recomputed from the target's reviewed publication state and exact edition/topic compatibility. An unpublished, retired, missing, or incompatible target renders an unavailable state, never a working link. RV-043 needs an actual compatible published next assessment for full progression acceptance.

### Required tests and review

TDD covers correct, valid-wrong, interpretative, malformed and extra-field answers; required/unscored prose; pre-finalization leakage through routes, props and prefetch; wrong/expired owner; duplicate and concurrent submissions; changed payload conflicts; transaction rollback; publication/hash/review mismatch; retirement behavior; and recommendation eligibility. Persistence tests run against PostgreSQL. Independent review is required for scoring, owner, privacy, publication, and final acceptance.

Examples for a reviewed question with options `option-a` and `option-b`, accepting only `option-a`: `{ kind: "ruleQuestion", optionId: "option-b" }` is a valid wrong answer and must finalize with 0; `option-z` is invalid. For a structured item with authored `actor-006`, `{ kind: "restartDiscipline", stopPlay: false, restart: "playOn", discipline: "none", offenderHandle: null }` is a valid wrong answer when the reviewed answer is a penalty; `{ kind: "restartDiscipline", stopPlay: false, restart: "penaltyKick", discipline: "none", offenderHandle: null }` is malformed. A required analysis answer with whitespace-only reasoning is malformed; one with a nonblank 1–600-code-point explanation is structurally valid even when its decision is wrong, and its reasoning remains unscored. A submission containing `score`, `ownerId`, or a hidden rubric field is invalid.

## Full-source authoring and publication boundary (proposed v2)

This contract supersedes the narrow `ScenarioInput` hash only for authored-training publication. Existing synthetic rows and tests retain their v1 identity until explicitly migrated. It does not assert that the first incident has passed rendered-evidence review.

### One canonical input

The normal authoring API accepts one `CanonicalScenarioSourceV2` value. It does not accept a caller-selected content hash, public/private projection, bound observation fixture, or publication state. The compiler validates and derives those outputs. Version 2 is limited to the approved clear, main-referee, 60 Hz, at-most-480-tick incident; other roles and classifications require new contracts.

The source has this exact top-level shape. Referenced types are `TimelineFixtureInputV2` from [`simulator-timeline.md#canonical-events-v2`](simulator-timeline.md#canonical-events-v2), plus the already versioned `FieldGeometry`, `DecisionGate`, `ObservationFixtureInput` (with its derived identity fields omitted), and `ClearPenaltyMainRefereeRubricV1`. A compiler must still validate their nested keys and cross-references rather than trusting TypeScript types.

```ts

  ref: { scenarioId: "incident-001"; version: number };
  classification: "clear"; supportedRoles: readonly ["mainReferee"];
  lawsEdition: "IFAB-2026-27";

  initialRefereePose: { position: { x: number; y: 0; z: number }; lookYaw: number; lookPitch: number };
  rendering: {
    assets: readonly AssetRecord[];
    actorBindings: readonly { actorId: string; rigAssetId: string; clipAssetIds: readonly string[] }[];
    safeCues: readonly { cueId: string; tick: number; ordinal: number; kind: "animationCue" | "audioCue"; assetId: string }[];
  };
  decisionOptions: readonly PublicDecisionOption[];
  officialSources: readonly OfficialSource[];
  facts: {
    passTick: 120; passerActorId: "attack-08"; receiverActorId: "attack-09"; onsideMarginM: number;
    contactTick: 366; offenderActorId: "defence-04";
    contactGround: { x: 13.8; y: 0; z: 36.8 };

  observation: Omit<ObservationFixtureInput,
    "ref" | "scenarioContentHash" | "durationTicks">;

      | { kind: "actorAttachment"; actorId: string; attachmentName: string }

  sourceId: string; edition: "IFAB-2026-27"; documentUrl: string;

```

The source contains these declared categories:

- `schemaVersion: 2`, `purpose: "authoredTraining"`, neutral `ref`, classification, role, and `IFAB-2026-27` edition.
- A versioned competition profile with the literal approved settings above. Its hash is derived from the normalized profile identity and settings, not accepted from the caller.
- Field geometry, complete canonical actor/ball timeline, safe cues, decision gate, and authored initial referee ground pose and look. The timeline has seven footballer IDs; the user-controlled referee is separate.
- Rendering dependencies: every procedural geometry definition or external asset byte fingerprint, declared rig attachment and geometry-part names, actor/cue binding, neutral client path, creator/origin, license evidence, and a stable canonical asset ID. Client handles and paths must not reveal the ruling.
- Official sources with stable IDs, exact edition, document URL, law/section locator, inspected artifact fingerprint, and provenance. `/latest/` links are navigation references only, not immutable edition fingerprints.
- Typed canonical facts, private evidence geometry/windows, observation model/rig/calibration versions, camera colliders, private decision/observation rubric, and the actual prepared Spanish and English debrief text with source/evidence references.

Any field needed to render, establish, evaluate, explain, or cite the incident is immutable source content. Publication review identity, reviewer, timestamps, and audit events are separate mutable lifecycle records and never enter the content hash. The source cannot contain bound `scenarioContentHash` fields to avoid self-reference; the compiler inserts its derived hash into downstream C1/C2 and public/private projections.

### Validation, normalization, and derivation

Reject unknown keys, non-plain objects, accessors, symbols, hidden properties, sparse arrays, non-JSON values, unsafe integers where ticks/versions are required, nonfinite numbers, and duplicate IDs. Reject unsupported editions, roles, versions, durations, or geometry. Validate all cross-references among actor roster, timeline events, cues, asset bindings, evidence anchors/occluders, geometry bindings, required evidence, rubric key, official sources, and debrief references. Every `(evidenceId, anchorId)` and `(evidenceId, boxId)` present in any sample has exactly one geometry binding for that evidence; no unused binding is allowed. Actor targets refer to the authored roster; their attachment/part names must be declared by that actor's bound rig asset.
