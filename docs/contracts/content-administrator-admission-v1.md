# Content administrator admission v1

## Scope

This contract governs trusted review admission and publication for Academy lessons and Assessment items. It does not publish any candidate, authenticate learners, approve football content, or change simulator publication. The existing anonymous session cannot act as a reviewer or administrator.

## Authority

- The first implementation is a local, server-only administrator CLI using a separately provisioned PostgreSQL reviewer credential. A distinct migration-only role owns schema, tables, triggers, and privileged procedures. The web application role and reviewer CLI role are non-owners, cannot inherit the migration role, and have no DDL, trigger-disabling, role-management, superuser, or bypass privileges. The application `DATABASE_URL` credential cannot insert, update, or delete content versions, reviews, revocations, publication rows, or events. The reviewer credential cannot directly update protected tables; it may execute only the reviewed draft-import, review-admission, withdrawal, and publication-transition procedures. The reviewer credential is never loaded by the web process, bundled, logged, or accepted from an HTTP request.
- Provision roles outside application migrations through a bootstrap administrator, first in isolated `refview_test`. Migrations use a required `MIGRATION_DATABASE_URL` with no fallback to `DATABASE_URL`; the web process receives only the restricted application credential. Keep migration and reviewer credentials outside the Next.js `.env` and runtime process. Test actual distinct logins, not a privileged login with `SET ROLE`. Before switching the local application credential, transfer only allowlisted existing objects to the migration owner and grant the existing owner lifecycle its needed narrow operations. Do not reassign all bootstrap-owned objects or reset the application database.
- V1 permits only direct review by Nicolas through his separately provisioned reviewer credential. Provisioning records evidence that the credential was issued to Nicolas and maps its authenticated PostgreSQL role to his stable principal; a display name, anonymous cookie, environment flag, or chat statement alone is insufficient. Importing a prior statement on another person's authority is out of scope for v1. The CLI resolves the actual actor from the database role/principal mapping. Input JSON cannot supply actor, reviewer principal, privilege, review time, or publication time.
- A direct Nicolas review requires an exact `(content kind, stable ID, version, server-derived source hash)` receipt and a digest of the exact reviewed evidence artifact. The receipt contains explicit affirmative decisions `footballInterpretationApproved`, `sourcesAndProvenanceApproved`, and `spanishEnglishEquivalenceApproved`; Assessment additionally requires `acceptedAlternativesApproved`, `correctionApproved`, and `rubricMeaningApproved`. All required decisions must be exactly `true` for admission as a positive review. False, missing, or extra decisions cannot be promoted. The CLI presents the exact identity/evidence and requires Nicolas's explicit confirmation while authenticated; it cannot derive approval from the presence of a hash alone.
- A denied or absent review cannot be promoted. Changed source bytes or hashes require a new version and review. Withdrawal of an admitted review locks the same publication row used by publish/retire, then checks current state and inserts an append-only revocation referencing its exact review ID and source triple. A publication transition checks revocation while holding that publication lock and rejects a revoked review. If content is already reviewed, withdrawal retires it and appends the retirement event in that same transaction; a draft remains draft and cannot later promote on the revoked receipt. Historical attribution and review bytes remain immutable.

## Storage and transitions

- Academy and Assessment have separate version, review, review-revocation, publication, and append-only publication-event tables with concrete foreign keys. A source version is immutable after draft import. The review binds the complete `(ID, version, contentHash)` triple; Assessment also stores and rechecks rubric version/hash. A publication row references a review for the same triple.
- The authenticated reviewer credential imports a compiled draft through a narrow migration-owned `import_draft` procedure called only by the reviewed CLI. That procedure creates the immutable version and initial draft publication in one transaction, with source identity and digest derived or verified inside SQL. Import grants no review or publication eligibility and cannot alter an existing `(ID, version)`. The web application credential has no import procedure grant. The migration credential owns and deploys the procedure but is not an application-time importer.
- The allowed state sequence is `draft -> reviewed -> retired`. `reviewed` means eligible for discovery or new attempts only after the trusted transition commits. Retirement blocks new discovery, recommendations, and starts while preserving historical pinned reads and already started Assessment attempt finalization. No reactivation or in-place source update exists.
- The reviewed administrator CLI opens one transaction and locks the publication row through an approved procedure. It recompiles the immutable stored source with the versioned TypeScript compiler and compares the exact canonical source bytes, computed content hash, and Assessment rubric identity before asking for approval or transition. Inside that same transaction, the privileged transition procedure independently verifies the stored UTF-8 envelope digest, source/review binding, revocation, expected revision, and legal state, then updates publication and appends an event with actual actor, reason, prior/next state, revision, exact source hash, and database timestamp atomically. PostgreSQL enforces bytes, identity, state, privileges, and audit invariants; the reviewed CLI and fail-closed application reads enforce source semantics. The reviewer credential is trusted to use the reviewed CLI. Direct application-role writes cannot bypass the boundary. Concurrency gives one winner per expected revision; audit failure rolls back the transition.
- The migration must enforce immutable version/review/revocation/event rows, monotonic revisions, valid initial state, and the migration-owner/application/reviewer privilege split in PostgreSQL. Privileged procedures have a pinned safe search path, fixed grants, and no caller-controlled SQL; only the migration role owns them. `Prisma` service checks alone do not replace database write restrictions.
- The application role cannot receive `UPDATE` on protected publication tables solely to obtain a row lock. A narrow migration-owned eligibility-and-lock procedure serializes Assessment starts with retirement and returns only the exact pinned approved identity; the surrounding transaction retains the lock. Restricted application owner locking similarly uses a reviewed narrow function instead of broad `UPDATE` on `AnonymousSession`.

## Reads and secrecy

- Draft import and stored reads recompile exact source JSON and compare server-derived hashes; Assessment also verifies rubric identity. A corrupt, mismatched, or missing reviewed binding fails closed. No fixture fallback is permitted for a claimed published row.
- Source versions store the exact canonical UTF-8 hash envelope alongside parsed source JSON. SQL parses the tagged envelope, checks its domain tag and extracted source JSON equal the stored source JSON and `(kind, ID, version)` identity, and verifies the digest over the original UTF-8 envelope bytes. For Assessment, SQL also checks the rubric envelope's tag and extracted JSON against the bound source's `privateRubric`, then verifies its digest; the rubric envelope itself has no item ID/version. SQL does not assume `jsonb::text` matches `canonicalJsonV2`. A reviewer who bypasses the CLI may submit semantically invalid but byte-consistent content; server-side readers must still reject it, and the documented administrator operation is the reviewed CLI.
- Published Academy reads expose reviewed lesson fields and prepared follow-ups. Practice eligibility is checked against the current exact target publication and topic/edition before a working link appears.
- Assessment catalog and active-attempt projections use explicit public DTO allowlists. The source compiler, private rubric, accepted alternatives, and correction stay server-only before finalization, including RSC payloads, action responses, metadata, prefetch, client bundles, and logs. Finalized owner-bound results reveal only the reviewed correction projection. Recommendation eligibility is computed from the current target publication.

## Verification and rollout

- Use synthetic review principals and source fixtures only in isolated `refview_test` PostgreSQL tests. Prove application and reviewer roles are non-owners without inherited migration rights; direct application/reviewer DML and DDL are rejected; approved procedures resolve actual actor from the database role, reject forged actor/reviewer/time fields, denied or incomplete decisions, and mismatched evidence/hash; revoked draft reviews cannot promote; revoking a published review retires atomically; a revocation-versus-publish race cannot commit reviewed content after withdrawal. Also prove immutable source/review/revocation/event rows, triple binding, revision races, retirement/start races, event rollback, read-time hash failure, historical continuity, and public DTO secrecy.
- The local application database may receive draft source records before Nicolas's review. It cannot receive a positive review or reviewed transition until the exact current hash is approved and trusted principal admission is independently verified. A local transition does not authorize deployment.
- Revoking a receipt retires a reviewed publication only if that exact receipt is its bound review; revoking an unbound historical receipt preserves a different valid bound review. Both withdrawal and transition take the same publication lock.
- Independent review is required for this contract, schema/role migration, administrator CLI, and final publication. Record approval, trusted admission, local publication state, and deployment as separate facts.
